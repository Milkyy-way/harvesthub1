# Checkpoint 0 — Auth foundation: login & signup (COMPLETE)

## Scope
Customer and farmer signup/login, fully separate flows, built entirely
on Supabase Auth + Postgres. This is the foundation every later
checkpoint (location, browse, cart, orders) builds on top of.

## What works end-to-end
- Separate signup/login screens for **customer** and **farmer** roles
  (different forms, different post-signup destinations)
- Supabase Auth handles account creation, session, and JWT issuance
- Email verification is implemented but currently **disabled** for
  testing (any email works) — flip back on when ready for real users
- Input validation on frontend: email format, phone number, required
  fields, basic security checks before submit
- A signup trigger (`handle_new_user()`, referenced in migration 0005)
  fires on account creation and inserts the correct profile rows
  automatically — customer or farmer never has to manually create
  their own `profiles`/`customer_profiles`/`farmer_profiles` row

## Database schema (Supabase Postgres)

**profiles** (shared identity/role table, one row per user)
- `id` (references `auth.users`), `role`, `status`
  (`active` / `pending_verification` / `rejected` / `suspended`),
  `full_name`, `phone`
- RLS: users can update only their own row; column-level grant
  restricts `authenticated` to updating only `full_name`/`phone` —
  `role` and `status` can't be self-edited (closes a self-approval
  security hole)

**customer_profiles** (one row per customer, filled at signup —
customers never need an authenticated follow-up step)
- `id` (references `profiles`), `address_street/city/state/zip`,
  `dietary_preferences[]`, `produce_interests[]`, `referral_source`
- RLS: private — only the customer themselves can read/update

**farmer_profiles** (created as a near-empty stub at signup, filled in
later via an authenticated onboarding wizard — file uploads need
`auth.uid()`, which only exists post-login)
- `id`, `farm_name`, address fields, `farm_types[]`,
  `years_in_operation`, `tax_id`
- RLS: private, self-only

**farmer_verification** (business/legal verification packet)
- license, insurance, food safety cert, gov ID, land proof, references
  (stored as file paths), `status`
  (`pending_verification` / `approved` / `rejected`), reviewer fields
- Farmers can edit their own submission fields only — **cannot** touch
  `status`, `reviewer_notes`, or `reviewed_by` (column-level grant,
  same technique as `profiles`)
- A trigger (`sync_profile_status_from_verification`) keeps
  `profiles.status` in sync whenever `farmer_verification.status`
  changes, so app code never has to update both manually

**farmer_certifications** (variable-length: organic, USDA, state ag
registration, etc. — a farmer can have zero or many)
- `farmer_id`, `cert_type`, `cert_name`, `file_path`
- RLS: farmers manage their own only (`for all`, self-only)

## Frontend project structure (Expo / React Native)
app/ — Expo Router screens
components/ — shared UI components
contexts/ — auth context, likely session/role state
hooks/ — custom hooks
lib/ — Supabase client, (soon) apiClient.ts
types/ — shared TypeScript types
constants/ — app-wide constants



# Checkpoint 1 — Customer location (COMPLETE)

## What works end-to-end
Expo app (Supabase login) → JWT (ES256, verified via Supabase JWKS)
→ FastAPI (`GET /api/v1/customers/me`) → SQLAlchemy → Supabase Postgres
(customer_profiles) → Census/zip geocoding fallback → JSON back to app.

## Files built
- app/core/config.py       — env settings (DATABASE_URL, SUPABASE_URL)
- app/core/database.py     — SQLAlchemy engine/session (get_db dependency)
- app/core/security.py     — JWT verification via Supabase JWKS (ES256)
- app/customers/models.py  — CustomerProfile (mirrors customer_profiles;
                              does NOT map dietary_preferences/
                              produce_interests/referral_source — unused so far)
- app/customers/service.py — get_or_geocode_profile(): geocodes full
                              address first, falls back to zip centroid,
                              marks geocoded_at either way so it only
                              ever attempts once per user
- app/customers/schemas.py — CustomerProfileOut
- app/customers/router.py  — GET /customers/me
- app/main.py               — FastAPI app, CORS, router registration
- alembic/versions/xxxx     — added latitude, longitude, geocoded_at
                              to customer_profiles (hand-written, no
                              autogenerate — table has other columns
                              our models don't map)

## Auth pattern (reused everywhere from here on)
Every protected route: user = Depends(get_current_user) →
always query by user["id"], never trust a client-supplied ID.
RLS is NOT enforced on FastAPI's direct connection (it connects as
postgres, bypassing RLS) — authorization is enforced in code instead.

## Frontend pattern (reused everywhere from here on)
lib/apiClient.ts — axios instance, interceptor calls
supabase.auth.getSession() before every request (handles silent
refresh automatically), attaches Bearer token. `baseURL` originally
hardcoded a LAN IP literal in this file; Checkpoint 2 moved it to
`EXPO_PUBLIC_API_BASE_URL` in `.env` (still your machine's LAN IP, found
via `ipconfig`, not localhost — just no longer buried in source).

## Migration discipline
Alembic migrations are hand-written, never --autogenerate (real tables
have many columns our SQLAlchemy models intentionally don't mirror).
alembic upgrade head is a manual, one-time action per migration —
never triggered by running the server.

## Known gap (fixed in Checkpoint 2 — see below)
Full-address geocoding will likely keep failing until real (non-test)
addresses are entered. `_geocode_zip_centroid()` existed since this
checkpoint but was **dead code** — `get_or_geocode_profile()` never called
it, and only re-attempted geocoding by checking `latitude is None` (so a
failed address was silently retried, uselessly, on every single request
instead of "attempt once"). Both bugs were fixed in Checkpoint 2: the zip
fallback is now actually wired in, and the "have we tried yet" check uses
`geocoded_at` instead of `latitude`.
Swap to Google/Mapbox geocoding later if street-level accuracy matters.



# Checkpoint 2 — Customer feed / home page (COMPLETE)

## Scope
Once a customer is logged in and geocoded, they land on a real home feed:
company header, search bar, horizontally-scrollable category rail, and a
list of farmer profile cards sorted by distance — filterable by category
tap or search text. A 4-tab bottom nav (Home/Search/Orders/Account) was
added; only Home has real content, the rest are placeholders. Tapping a
farmer card navigates to a placeholder detail route — the actual
items/price/qty-stepper/add-to-cart page is deliberately out of scope,
next checkpoint. This was greenfield: no farmers/products/categories/cart
module existed anywhere in the backend before this, and no tab bar,
search bar, category chips, or card list existed anywhere in the frontend.

## Database schema (new)
**categories** — id, slug (checked against the 8 known produce_interests
values), name, sort_order, icon_name. Seeded with all 8 rows in the same
migration. Public read policy (no write policy — managed by hand).

**products** — id, farmer_id → profiles, category_id → categories
(on delete restrict), name, description, price, unit (free text — no
enum yet, real product CRUD is next checkpoint), quantity_available,
image_url (unpopulated so far — no upload UI built yet, see Known gaps),
is_active, timestamps. RLS: public read for active products (or the
owning farmer sees their own inactive ones too); farmers manage their own.
Indexed on farmer_id, category_id, and a partial index on
(category_id, farmer_id) where is_active, for the feed's per-farmer
"does this farmer carry a matching product" EXISTS filter.

**farmer_profiles** gained latitude/longitude/geocoded_at (mirrors
customer_profiles from Checkpoint 1, geocoded the same way — full-address
Census lookup, zip-centroid fallback, attempt once) and photo_url (the
farm's store/logo photo shown on its feed card).

**New public storage bucket `farmer-photos`** (5MB, jpeg/png/heic) — public,
unlike `farmer-verification-docs`, since customers who aren't the owning
farmer need to load it. Path convention `{uid}/farm-photo.<ext>`.

**Migration files**: `supabase/migrations/0008_categories_and_products.sql`,
`0009_farmer_geo_and_photo.sql`, `0010_seed_sample_farmers_and_products.sql`
(dev/test data only — 5 fake farmers with real coordinates clustered
around Fresno, CA + 15 products across categories, so the feed has
something to sort/filter during development). `alembic/versions/
14e2f8ac5990_...py` mirrors the narrow column set FastAPI's models need,
written as raw `IF NOT EXISTS` SQL (not `add_column`/`create_table`) so it
stays safe to run regardless of whether the Supabase SQL migrations already
ran against the same database — same reasoning as Checkpoint 1's migration,
now stated explicitly as the pattern.

## Backend — new modules
- **app/categories/** (full module) — `GET /categories`, ordered by
  sort_order.
- **app/farmers/** (full module, first FastAPI model for farmer_profiles
  despite the table existing since Checkpoint 0) — `GET /farmers/feed`

  counts grow large.
- **app/products/** — models.py only (farmer_id, category_id, name,
  is_active — just enough for the feed's EXISTS filter), no router/service
  yet. Real product CRUD is next checkpoint's job; this avoids scaffolding
  that would need reworking then.
- **app/main.py** now registers categories_router and farmers_router
  alongside customers_router, same /api/v1 prefix pattern.

## Bugs found and fixed during this checkpoint (non-obvious — read before touching this code)
- **Pydantic v2 doesn't auto-coerce UUID → str.** `CategoryOut.id: str`
  fed a raw SQLAlchemy `Category.id` (a `uuid.UUID` object) 500'd on
  every request — silently, since the frontend only console.warn'd the
  failure, so the category rail just rendered empty with no visible
  error. Fixed by having `list_categories()` return already-stringified
  dicts, matching the pattern app/farmers/service.py used from the start
  (`"id": str(farmer.id)`). **If you add another endpoint that exposes a
  raw id field, stringify it explicitly — don't rely on response_model
  coercion.**
- **Seeding fake auth.users rows fires the real handle_new_user() trigger**
  (0001/0005) — the same one a real signup fires. The first version of
  0010 passed empty `raw_user_meta_data`, so the trigger defaulted every
  seed account to role:"customer" and tried inserting a customer_profiles
  row with no address, violating a NOT NULL constraint. Fixed by passing
  `role:"farmer"` + `farm_name` in the metadata so the trigger creates the
  farmer rows itself, then a plain UPDATE fills in the rest (address, geo,
  photo) and flips farmer_verification to 'approved' (which the existing
  sync trigger turns into profiles.status='active' automatically) — no
  fighting the trigger, just feeding it what a real signup would.
- **`products` seed insert had no explicit id**, so `on conflict do
  nothing` was a no-op (a fresh gen_random_uuid() default never collides)
  — re-running the seed file would have silently duplicated all 15
  products every time. Fixed with explicit fixed ids, `on conflict (id)`.
- **Icon font not preloaded → first-paint rendering glitch.** MaterialIcons
  (used via IconSymbol and direct @expo/vector-icons imports throughout
  the new customer UI) could render blank/garbled on the very first frame
  after a cold launch, self-resolving after any re-render — this app's
  custom root layout never adopted the standard Expo Router template's
  font-preload pattern when it was built. Fixed in app/_layout.tsx with
  `useFonts({ ...MaterialIcons.font })` gating render behind
  expo-splash-screen, the textbook fix for this class of symptom.
- Two screens were missing safe-area handling (Header overlapping the
  status bar; the farmer-detail back button cramped in the corner) —
  neither existing screen in this app touched the top edge before this
  checkpoint (all were centered-content placeholders), so this gap was
  invisible until a top-anchored screen was actually built. Fixed with
  `useSafeAreaInsets()` (react-native-safe-area-context, already installed).

## Known gaps / next checkpoint (as of Checkpoint 2)
Farmer detail page (items, price, qty stepper, add-to-cart), cart, orders,
ratings/reviews, favorites — all unbuilt; `farmer/[id].tsx` is a

# Checkpoint 3 — Farm detail page, product catalog, cart (COMPLETE)

## Scope
`farmer/[id].tsx` (a placeholder since Checkpoint 2) is now the real farm
detail page: header (photo, location, distance, years in operation, farm
types, bio, certification badges), a category filter bar scoped to only
the categories this farm actually carries, and a product list — alphabetical
by name, out-of-stock items dimmed and non-interactive, low-stock items
(<11 available) showing the exact remaining count, and a +/- stepper on
each in-stock item backed by a real per-customer cart persisted in
Postgres. A sticky bottom bar shows a running item count/total that stays
correct even while a category filter hides some items, since it's derived
from the full unfiltered product list, not the filtered view.

## Database schema (new)
**farmer_profiles** gained `bio` (text, nullable — filled in later via a
farmer profile-edit UI that doesn't exist yet, same "required enforced
client-side, not at the DB level" pattern as the rest of this table).

**cart_items** — one row per (customer_id, product_id), `unique
(customer_id, product_id)` enforces at most one row per pairing;
`quantity` (checked > 0 — a row is deleted rather than zeroed). FK to
`profiles` (customer) and `products`, both `on delete cascade`. RLS:
self-only, `for all` — same caveat as every other table here: FastAPI's
direct connection bypasses RLS, so this policy only matters for a future
direct supabase-js path, not the `/cart` endpoints themselves.

**Migration files**: `supabase/migrations/0011_farmer_bio_and_cart.sql`;
`alembic/versions/7c2a91f5e8b4_...py` mirrors the narrow column set
FastAPI's models now need — `farmer_profiles.farm_types`/
`years_in_operation`/`bio` (the first two existed since 0004 but were
never mapped into `FarmerProfile` until this checkpoint), `products`'
`description`/`price`/`unit`/`quantity_available`/`image_url` (existed
since 0008, same story), plus `CREATE TABLE IF NOT EXISTS` for the two
brand-new tables (`farmer_certifications`, `cart_items`) — same "safe
regardless of whether the Supabase SQL migrations already ran" raw-SQL
discipline as `14e2f8ac5990`.

## Backend — new/changed modules
- **app/farmers/models.py** — `FarmerProfile` now maps `farm_types`,
  `years_in_operation`, `bio`. New `FarmerCertification` model (id,
  farmer_id, cert_type, cert_name) — deliberately excludes `file_path`,
  which is private verification-adjacent data with no reason to ever reach
  a customer-facing endpoint.
- **app/farmers/service.py / router.py** — new `GET /farmers/{farmer_id}`
  (registered *after* `/feed` in the router — a `{farmer_id}` route
  declared first would shadow the literal `/feed` path, matching it as
  `farmer_id="feed"`). Same visibility rule as the feed
  (`role == "farmer" and status == "active"`) so a suspended/unapproved
  farmer's page 404s instead of leaking. Reuses `get_or_geocode_farmer`
  and `haversine_km` from Checkpoint 2 to include `distance_km` in the
  header. Auth via the existing `get_current_customer`.
- **app/products/** (now a full module — was models-only since
  Checkpoint 2). `models.py` expanded to map `description`, `price`,
  `unit`, `quantity_available`, `image_url`. New `schemas.py`/`service.py`/
  `router.py` — `GET /products?farmer_id=&category=` (category is a slug,
  matching the feed endpoint's existing convention, not a raw category id),
  active products only, joined against `profiles` for the same
  active-farmer visibility check as above, sorted case-insensitively by
  name at the DB level (`ORDER BY lower(name)`). Each returned product
  includes the *current customer's own* `cart_quantity` (a join against
  `cart_items`) so the frontend's stepper renders correctly on first load
  without a separate `/cart` round trip.
- **app/cart/** (brand new module) — `GET /cart` (full per-customer cart
  across every farm — not used by the farm detail page today, but the
  obvious foundation for a future multi-farm cart/checkout screen);
  `POST /cart/items/{product_id}/increment` and `.../decrement`, both
  auth'd via `get_current_customer` and returning the product's new
  quantity plus the customer's overall cart total/count. `increment`
  404s on an inactive/missing product and 409s if the customer's existing
  quantity has already reached `quantity_available` (no oversell past
  what one farmer has on hand). `decrement` deletes the row once quantity
  would hit zero rather than storing a zero row.
- **app/main.py** now also registers `products_router` and `cart_router`.

## Frontend — routing, components, state
`app/(customer)/farmer/[id].tsx` fully rewritten (was Checkpoint 2's
"coming soon" stub) — no routing changes needed, since the dynamic
`/(customer)/farmer/[id]` route and the home feed's `router.push` into it
already existed. Fetches farmer detail, the global `/categories` list, and
this farm's full (unfiltered) product list once on mount; category
selection and alphabetical sorting happen **client-side** against that
already-fetched list rather than re-querying the backend on every filter
tap (the dataset is small per farm, and computing the running total from
the full list — not whatever subset is currently filtered — is what keeps
the sticky total bar accurate while a filter is active). The category rail
itself reuses Checkpoint 2's `CategoryRail` component unchanged, filtered
down to only the slugs this farm's products actually carry.

New `components/customer/`: `FarmerDetailHeader` (photo + back button,
location/distance line, years-in-operation, farm-type chips, bio,
certification badges), `ProductCard` (photo, name, price/unit, low-stock/
out-of-stock messaging, +/- stepper), `CartTotalBar` (sticky footer,
renders nothing when the cart for this farm is empty). All three follow
the same visual conventions as Checkpoint 2's `FarmerCard`/`Header`
(same shadow/radius/spacing tokens, same "photo fails to load → icon
fallback" pattern via a local `imageFailed` state).

Cart mutations (`handleIncrement`/`handleDecrement` in the screen) update
local state optimistically, then reconcile with the backend's returned
quantity on success or roll back on failure (e.g. a 409 from racing past
`quantity_available`) — never fires while a request for that same product
is already in flight (`pendingProductId` gate), so rapid tapping can't
desync local state from the server. Cart state is fully backend-persisted
(`cart_items`, keyed by the authenticated customer), not component state —
navigating away and back, or a fresh app launch, re-reads real quantities
via each product's `cart_quantity` field, so the existing session-based
auth flow (Checkpoint 0/1's JWT-in-`apiClient`) already satisfies "no
re-authentication needed to keep cart state."

## Known gaps / next checkpoint (as of Checkpoint 3)
Checkout/order placement, a multi-farm "my cart" screen (the `GET /cart`
endpoint exists for this but has no frontend consumer yet), ratings/
reviews, favorites — still unbuilt. Per-item product photo upload is still
unbuilt (`products.image_url` stays null for every seeded product; the
`ProductCard` photo fallback icon is what actually renders today).
`farmer_certifications` has no farmer-facing CRUD yet — populating it for
a real (non-seed) farmer currently requires a direct Studio table edit.



# Checkpoint 4 — Cart screen: multi-farmer grouping + fulfillment choice (COMPLETE)

## Scope
`GET /cart` (built in Checkpoint 3 but unconsumed) now has a real frontend:
a dedicated cart screen showing every farm currently in the customer's
cart as its own section — items, per-item qty stepper/remove, farm
subtotal — plus a pickup-or-delivery choice **per farm**, not once for the
whole cart. This is a deliberate business decision, not a default: the
cart can span multiple farmers (blocking that would fight the app's core
"browse nearby farms" premise), but checkout (next checkpoint) splits it
into one order per farmer, so fulfillment has to be chosen per farmer too.
A "Continue to Checkout" button is disabled until every farm group has a
method chosen (and a filled delivery address, if delivery); pressing it
today shows a placeholder — actual order placement is Checkpoint 5.

## Design decisions worth knowing before extending this
- **No new tables.** Pickup uses each farm's own address/coordinates
  (already in `farmer_profiles`) via a "Get Directions" deep link
  (`lib/maps.ts` — native `maps:`/`geo:` URL scheme with an `https://
  www.google.com/maps/...` fallback, no API key, no `react-native-maps`
  dependency, no embedded map view). If farmers ever need to register
  pickup sites separate from their home address (e.g. a farmers-market
  booth), that's new schema + a farmer-facing management UI — a
  meaningfully bigger feature, deliberately not built here.
- **Delivery address is a one-off per-order override, not a saved address
  book.** Prefilled from `customerProfile` (Checkpoint 1's geocoded
  address), editable inline via the existing `TextField` component,
  state lives only in the cart screen — nothing is persisted until an
  actual order is placed.
- **Fulfillment choice is `Record<farmerId, {...}>` component state**,
  not written to the backend at all yet — there's no order/draft-order row
  for it to live on until Checkpoint 5 builds order creation. Whatever
  checkout ships next needs to either accept this shape directly from the
  cart screen (e.g. as navigation params) or the cart screen needs to
  start persisting it — an open decision for that checkpoint, not resolved
  here.

## Backend — changed
- **app/cart/schemas.py** — `CartSummary` reshaped from a flat item list
  into `{ farms: CartFarmGroupOut[], total, item_count }`; each
  `CartFarmGroupOut` carries the farm's name/photo/address/coordinates
  alongside its items and subtotal, specifically so the cart screen can
  render a pickup option without a second request per farmer.
- **app/cart/service.py** — `get_cart()` rewritten to group by farmer
  (was flat); new `remove_item()` — deletes a cart row outright regardless
  of quantity (the cart screen's trash icon), distinct from `decrement_item`
  which only steps down by one. `increment_item`/`decrement_item` and their
  409/404 behavior are unchanged from Checkpoint 3.
- **app/cart/router.py** — new `DELETE /cart/items/{product_id}` wired to
  `remove_item`. `GET /cart` and the two POST endpoints are unchanged
  paths, just a reshaped response body on `GET /cart`.

## Frontend — new screen, components, entry points
- **app/(customer)/cart.tsx** (new stack screen, registered in
  `(customer)/_layout.tsx`) — fetches `/cart` on every focus (via
  `useFocusEffect`, not just mount, since the cart can change on the farm
  detail screen or this screen itself and should stay current when
  navigating back in). Cart mutations follow the same optimistic-update
  pattern as Checkpoint 3's farm detail page, except a failed/conflicting
  mutation triggers a full `loadCart()` refetch rather than a hand-rolled
  rollback — simpler, and correct by construction against a 409 stock
  conflict where "what the value was before" isn't the right rollback
  target anyway.
- New `components/customer/`: `CartLineItemRow` (name/price/qty stepper/
  remove, plus a warning if `quantity` now exceeds `quantity_available` —
  e.g. a farmer lowered stock after the item was added), `FulfillmentSelector`
  (pickup/delivery toggle + the address form, reusable per farm group),
  `CartFarmSection` (wraps one farm's header/items/subtotal/
  `FulfillmentSelector` together). `FulfillmentSelector`'s delivery form
  reuses the existing shared `TextField` component (from farmer/customer
  signup) rather than introducing a new input style.
- **Cart entry points** (none existed before this checkpoint):
  `CartTotalBar` (Checkpoint 3's sticky total bar on the farm detail page)
  gained an optional `onPress`, now wired to navigate to `/cart`. `Header`
  (Checkpoint 2's component, shown on the Home tab) gained an optional
  cart icon + item-count badge, wired the same way; Home fetches
  `GET /cart` on every focus purely to keep that badge's count current
  (`app/(customer)/(tabs)/index.tsx`).
- `.expo/types/router.d.ts` (Expo Router's auto-generated, gitignored
  typed-routes file) was stale after adding `cart.tsx` — hand-patched here
  only so `tsc --noEmit` could verify the rest of this checkpoint's code
  standalone; it regenerates correctly and automatically the next time
  `npx expo start` runs, no action needed.

## Known gaps / next checkpoint (as of Checkpoint 4)
Checkout/order placement is the whole next checkpoint: turning each farm
group + its chosen fulfillment (and delivery address, if applicable) into

# Checkpoint 6 — Orders, Stripe payment, cancellation/refunds, order history (COMPLETE)

## Scope
The accounting schema flagged as unresolved in Checkpoint 5 is now built —
`orders` → `store_orders` → `store_order_items`, plus `payments`,
`refunds`, `order_cancellations`, `payment_cancellations`. "Place Order" on
the checkout screen is real: it creates these rows, charges the customer
via a native Stripe PaymentSheet (or records a cash-on-pickup order with
no Stripe involvement), and lands on a real order confirmation/detail
screen. The Orders tab (3rd tab, "coming soon" since Checkpoint 2) is now

levels the user asked for — one farm within an order, or the whole
order — with a real (test-mode) Stripe refund issued for anything already
paid.

## Decision made this checkpoint: Stripe integration mechanism
Asked the user directly (not guessed) because it changes their dev
workflow, not just the code: **native Stripe SDK (PaymentSheet)**, over
the hosted-Checkout-page alternative. Consequence: `@stripe/stripe-react-
native` is a native module — **Expo Go no longer works for this app.**
Testing now requires a custom dev client (`npx expo prebuild` +
`npx expo run:ios`/`run:android`, or an EAS Build). See "What to do" below.

## Payment architecture — one PaymentIntent per `orders` row, not per farm
The customer's card is charged **once** per "Place Order" action, covering
the combined grand total across every farm in that checkout — not one
Stripe charge per farmer. "Every transaction happens separately" is
satisfied at the *bookkeeping* level instead: each `store_orders` row has
its own status, its own snapshot totals, and can be independently
cancelled/refunded — a targeted partial refund against the one shared
PaymentIntent, scoped to just that farmer's portion. This was a deliberate
trade-off, not an oversight: Stripe Checkout/PaymentSheet doesn't support
splitting one customer action into N separate charges to N different
farmers without Stripe Connect (a farmer-payout/onboarding system that
doesn't exist yet — see Checkpoint 5's payout-model gap, still unresolved).
Cancelling ALL farms in a still-unpaid order cancels the whole PaymentIntent;
cancelling ONE farm out of several *still-unpaid* farms shrinks the
PaymentIntent's amount instead (`stripe.PaymentIntent.modify`) so the
others can still complete payment — if Stripe won't allow that modification
(e.g. payment already in flight), the customer is told to cancel the whole
order and re-checkout rather than silently doing something financially
wrong.

## Explicitly deferred / simplified — flagged, not silently decided
- **Stripe Connect / farmer payouts** — still not built (see Checkpoint 5).
  Every dollar charged today goes to the platform's own Stripe account.
- **Inventory timing**: stock is decremented and the cart is cleared only
  once a card payment actually *succeeds* (webhook or the app's own sync
  call) — never at order-creation — so a declined or abandoned payment
  never locks stock or empties a cart for nothing. `cash_on_pickup` has no
  such failure mode, so it commits both immediately at creation. No
  reservation/hold system exists for the gap between "order created" and
  "payment confirmed" — acceptable at current scale, a known simplification.
- **No retry-payment flow.** A failed/abandoned card payment leaves its
  order sitting in the Active tab, still cancellable, but there's no "try
  paying again" button — only a fresh checkout.
- **`payment_method` collapsed to `'card' | 'cash_on_pickup'`** (dropped
  a separate `'wallet'` value from the original schema draft) — the native
  PaymentSheet decides internally whether to show Apple Pay/Google Pay
  next to the card form; the app never learns which the customer actually
  used, so a separate pre-selection was misleading.
- **`app.json`'s Stripe `merchantIdentifier`** (`merchant.com.harvesthub.app`)
  is a placeholder — real Apple Pay requires registering an actual merchant
  ID with Apple. Harmless today since `initPaymentSheet()` isn't passed an
  `applePay` config block, so Apple Pay isn't actually offered yet even
  though the plugin is wired in (the field just has to be *some* string or
  the native build config plugin crashes).
- **`promo_codes.times_used`**: still never incremented (flagged since
  Checkpoint 5) — redemption tracking needs deciding whether a cancelled/
  refunded order should "give back" its usage, which is now a real question
  with real cancel/refund flows to reconcile against, not just a stub.

## Database schema (new) — supabase/migrations/0013_orders_and_payments.sql
Seven tables, described in the migration's own header comment in full;
summary:
- **orders** — one per "Place Order" action. `status` (`active`/
  `completed`/`cancelled`) is **trigger-maintained**, not application-set
  (`sync_order_status_from_store_orders()`): all-cancelled → cancelled;
  all-non-cancelled-are-completed → completed; otherwise → active. Same
  "derived status kept in sync by a trigger" pattern as 0004's
  `sync_profile_status_from_verification`.
- **store_orders** — one per farmer per order; the real unit of
  fulfillment/cancellation/refund. Every address/price/fee field is a
  frozen snapshot (never re-joined against `farmer_profiles`/`products`
  for historical display — those can change or be deleted later).
  `status`: `pending_payment` → `paid` → `completed`, or → `cancelled`
  from either of the first two. `completed` is reachable today only via
  the customer's own "Mark as Received" button — no farmer-side
  fulfillment tool exists to transition it automatically yet.
- **store_order_items** — one per product line, `product_id` nullable +
  `ON DELETE SET NULL` (a deleted product must not break historical order
  display, which reads entirely from this row's own snapshot columns).
- **order_cancellations** — audit trail (`cancelled_by`, `cancelled_by_role`,
  `reason`); `store_order_id` is always the real unit cancelled, `order_id`
  groups every row from the same whole-order-cancel action together.
- **payments** — one per `orders` row (not per `store_orders` — see the
  architecture note above). `status` mirrors Stripe's own PaymentIntent
  status enum directly rather than a parallel state machine.
- **refunds** — always scoped to one `store_order_id` even for a whole-
  order refund (which just inserts one row per affected store); amount is
  independent of `store_orders.total`, which stays an immutable historical
  record — "how much has actually been kept" is `total - sum(refunds)`,
  computed at read time, never written back onto `total`.
- **payment_cancellations** — distinct from refunds: for a PaymentIntent
  that never captured any money (abandoned sheet, or explicitly cancelled
  while still unpaid) — nothing to refund, just an audit record.

Alembic mirror: `alembic/versions/9a4b6e2c7f31_add_orders_and_payments.py`
(same raw `CREATE TABLE IF NOT EXISTS` discipline; triggers/RLS are Supabase-
SQL-only, per every prior revision's own stated convention).

# Post-Checkpoint-6 fix — migration idempotency sweep (COMPLETE)

## What happened
Re-running `0013_orders_and_payments.sql` after a first partial failure hit
`policy "..." already exists`, then (after that fix) `trigger "..." already
exists`. Root cause: Postgres has no `CREATE POLICY IF NOT EXISTS` or
`CREATE TRIGGER IF NOT EXISTS` — a bare `create policy`/`create trigger`
only ever succeeds once. Investigating turned up that this wasn't unique to
0013: **every** migration file in the project had the same latent gap
(0001, 0003, 0004, 0006, 0008, 0009, 0011, 0012), plus a bare `add column`
in 0002 — it just never surfaced before since nothing had ever needed a
second run until 0013.

## Fix
Every `create policy` now has a `drop policy if exists "name" on table;`
immediately before it; every `create trigger` likewise has
`drop trigger if exists name on table;`; 0002's `add column` gained
`if not exists`. Verified with a project-wide sweep (every file, every
statement) that the counts balance 1:1 and nothing is unguarded anymore.
**No action needed for 0001–0012** — they already succeeded in the live
database; this is future-proofing only (a from-scratch Supabase project
setup, or any future partial-failure retry, won't hit this class of bug
again). 0013 itself needed re-running after the fix, which the user did.

  new backend endpoint**. Name/phone update `profiles` directly via
  supabase-js (the same column-grant this project set up in
  `0002_profiles_status_and_grants.sql` already permits exactly
  `full_name`/`phone`); address/preferences update `customer_profiles`
  directly too (its RLS policy allows a full self-update, unlike
  `profiles`). The one thing this had to get right: if the address
  actually changed, the update also nulls `latitude`/`longitude`/
  `geocoded_at` in the same call — otherwise `get_or_geocode_profile()`
  would never notice the address changed (it only re-geocodes when
  `geocoded_at is null`) and the customer would keep showing up at their
  old location in every farmer's distance sort. Saving calls the existing
  `refreshProfile()` from `AuthContext`, which re-triggers a fresh
  `/customers/me` fetch (and therefore a fresh geocode) automatically.
- `.expo/types/router.d.ts` hand-patched again for the new `edit-profile`
  route — same self-heals-on-next-`expo start` pattern as every prior
  checkpoint's new route.

## Known gaps / next checkpoint
No farmer-facing equivalent of any of this yet (farmer dashboard, farmer
account/profile editing). Dietary/produce preferences are editable but
`referral_source`/`referral_source_other` (captured at signup) still
aren't surfaced anywhere. The Account tab's address section and Edit
Profile screen don't yet show a "saving..." distinction between the
profile-table update and the customer-profile-table update — a partial
failure (e.g. the first `update` succeeds, the second fails) leaves the
two tables briefly inconsistent until the customer retries; low-risk at
this scale but worth a transactional RPC if it ever matters.
